# 本周产品更新：技能默认按需加载

**主题行：** 本周更新：技能改成按需加载

**预览文字：** 常驻的只有一行名片，正文命中才展开——这周我们把技能加载改成了三层。

---

## 开场

这周的主要变化不在界面上，而在上下文怎么花。我们把 Agent Skills 的加载方式改成了"常驻元数据、按需展开正文"：启动时不再把每份技能说明全量塞进提示，而是先看索引、命中再读正文。你看不到这条更新，但你的 agent 会更少选错技能，也更愿意把一份规范读完。

## 一、常驻的只有名片，不是简历

技能索引现在只带两样东西：`name` 和一行 `description`，每个技能 1–3 行。启动阶段只扫描元数据，正文一个字都不读。二十个技能从"每次推理都要参与"变成"先花几行 token 决定用谁"。

把 `description` 收进一屏以内，是这次改动最直接的收益：上下文窗口是预算，注意力是更稀缺的资源。

## 二、description 现在是真的接口

第一层是唯一的决策输入，所以描述写得好不好，直接决定路由准不准。有用的不是"这个技能很强大"，而是两个问题的答案：用户会用什么话触发它？什么时候该用它而不是邻居技能？

写模糊的描述，等于让 agent 在雾里选工具。这次更新后，我们建议你把触发词直接写进 `description`。

## 三、正文与支持文件分了三层

`SKILL.md` 正文只在技能被选中时读取；脚本、模板、参考资料再晚一层，执行到具体步骤才访问。代价逐层增加，上下文里流动的永远只是当下需要的那一块。

判断标准很简单：超过约 200 行的技能文件，把示例和模板挪到 `reference/`、`scripts/`、`templates/`，正文只留工作流和决策规则。

## 四、加载也要能回读验证

"加载了"不等于"读到了"，"读到了"不等于"用上了"。所以这次一并强化的还有验证习惯：产物落到固定路径再回读检查结构，而不是相信一句"已完成"；每次会话记录"索引了几个技能 / 实际加载了哪几个"。

路由命中率比 token 账单更早暴露问题。四个指标一起看才有意义——常驻 token 总量、单次任务的加载次数、选错技能的比例、任务完成率。

## 下一步：切开你最大的那个 SKILL.md

打开你项目里行数最多的那个 `SKILL.md`，把正文按"工作流 / 参考 / 模板"三段切开，只让第一段留在技能文件里。

改完回这封邮件，告诉我们你切掉了多少行、省下多少常驻 token——下周的更新里我们会挑几个真实数字出来聊。
